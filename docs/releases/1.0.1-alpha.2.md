# Flame iOS SDK 1.0.1-alpha.2 版本快照

> **版本性质**：预发布修复版（P0 闪退修复 + TB 打包缺陷修复）
> **发布日期**：2026-08-26
> **Git Tag**：`1.0.1-alpha.2`（二进制分发仓库 javaice007/flame_sdk_ios）
> **前一版本**：1.0.1-alpha.1（TK 线验证通过；TB 线真机不闪退但存在打包缺陷，已被本版取代）
> **详情索引**：`docs/releases/README.md`

## 修复的问题

### 1. P0：1.0.0 接入即启动闪退（承接 alpha.1，TK/TB 双线）

根因与修复同 `1.0.1-alpha.1.md`：动态产物对 ToBid 8 个 WindMill 类符号的扁平命名空间
延迟解析在静态产物下根除。**验证工程实测**（adsurge-ios-demo，Xcode 26.5 / iPhone 16 Pro）：

| 版本 | 产物形态 | 集成体验 | 真机启动 |
|---|---|---|---|
| `flame_sdk_ios` 1.0.0（TK） | 动态库 | 可构建 | ❌ dyld 闪退 |
| `flame_sdk_ios_tb` 1.0.0（TB） | 动态库 | 可构建 | ❌ dyld 闪退 |
| `flame_sdk_ios_tb` 1.0.1-alpha.1（TB） | 静态库 | ⚠️ 需绕过才能构建 | ✅ 不闪退 |
| `flame_sdk_ios` 1.0.1-alpha.1（TK） | 静态库 | ✅ 开箱即用 | ✅ 不闪退 |

### 2. TB 包打包缺陷（alpha.1 引入，本版修复）

**现象**：alpha.1 的 TB 产物外壳名 `flame_sdk_ios_tb.xcframework` 与内部 framework 名
`flame_sdk_ios.framework` 不一致，CocoaPods 按外壳名生成链接 flag：

```text
-framework "flame_sdk_ios_tb" → ld: framework 'flame_sdk_ios_tb' not found
```

客户工程默认集成无法构建（真机不闪退，但无法开箱即用）。TK 包外壳名与内部名一致，无此问题。

**修复**：TB 产物外壳统一为 `flame_sdk_ios.xcframework`（与 TK 包同构），与 TK 产物的
同名冲突通过**目录**区分——二进制仓库 TB 产物放 `tb/` 子目录，TB podspec 改为：

```ruby
s.vendored_frameworks = 'tb/flame_sdk_ios.xcframework'
```

module/import/API 全部不变（内部 framework 仍为 flame_sdk_ios.framework）。

## 已知限制（未在本版处理）

- 模拟器切片仍为 x86_64-only（继承自三方 adapter 依赖链限制：ToBid/AnyThink 的
  adapter xcframework 缺 arm64-simulator slice，客户工程在 Apple Silicon 模拟器上
  需 Rosetta）。flame 自体补充 arm64-sim slice 无法单独解决该链路问题，留待三方
  依赖支持后统一处理。
- 1.0.1-alpha.1 的 TB spec 保留在 flame-specs（tag 不可覆盖），CHANGELOG 已标注废弃。

## 升级指引（客户侧）

```ruby
# TK 客户
pod 'flame_sdk_ios', '1.0.1-alpha.2'
# ToBid 客户
pod 'flame_sdk_ios_tb', '1.0.1-alpha.2'
```

无需任何代码改动。请勿使用 1.0.0（启动闪退）与 1.0.1-alpha.1 的 TB 包（打包缺陷）；
TK 线 alpha.1 可用但建议统一 alpha.2。
