# Flame iOS SDK 1.0.1-alpha.4 版本快照

> **版本性质**：预发布版（发奖回调修复——按 Taku 官方文档修正 transId 取值来源）
> **发布日期**：2026-08-31
> **Git Tag**：`1.0.1-alpha.4`（二进制分发仓库 javaice007/flame_sdk_ios）
> **前一版本**：1.0.1-alpha.3（TK transId / TB userCustomData 发奖修复）
> **详情索引**：`docs/releases/README.md`

## 设计原则

**transId 只回传平台真实交易号，平台没给就是空串——SDK 不本地伪造 id。**
伪造值（如 UUID）会让接收方无法分辨 id 的真实来源与对账语义；空值 + 来源诊断日志
（`[TK_REWARD_DIAG]` / `[TB_REWARD_DIAG]`）才是可排查的诚实行为。

## 改动内容

### 1. TK 线：transId 取值链改为官方对账凭证（展示唯一 ID）

alpha.3 的取值链（发奖 extra 的 `third_trans_id` → Flame UUID 兜底）经 Taku 官方文档
复核存在两处偏差，本版修正：

- **`third_trans_id` 无文档依据**：三篇官方文档（激励视频 /docs/DUxiCT、服务端激励
  /docs/msbnkj、回调信息说明 /docs/pGEB4p）均未在发奖回调语境提及该 key，移除。
- **UUID 兜底取消**：见上方设计原则。

文档依据（/docs/msbnkj §3.2）：服务端 `trans_id` 由 Taku 服务端生成、唯一，"对应
客户端展示回调信息中的 getShowId()"（Android 命名；iOS 即展示回调 extra 的
`kATADDelegateExtraIDKey`，ATAPI.h:38 "a unique ID generated for each impression"，
/docs/pGEB4p 字段表中列为 `id`＝"展示唯一ID"）。

修正后取值链（`adapter/tk/AtRewardAdapter.m`）：

```text
发奖 extra 的 kATADDelegateExtraIDKey（展示唯一ID）
  → 展示回调（rewardedVideoDidStartPlaying）捕获的同一 ID（快照兜底）
    → 空串（平台未回传，日志 src=none 明示）
```

`src=topon-show-id(*)` 时客户端 transId 与 Taku 服务端激励回调的 `trans_id` 同源，
可直接配对对账。

### 2. TK 线：userCustomData 补写官方服务端回传通道（kATAdLoadingExtraMediaExtraKey）

文档依据（/docs/msbnkj §4.2 官方示例）：用户自定义数据走
`kATAdLoadingExtraMediaExtraKey`，随服务端激励回调 URL 回传开发者服务器。此前胶水只写
`kATAdLoadingExtraUserDataKeywordKey`（头文件归类 "Third-party extra data"，面向三方
网络透传），Taku 自身服务端激励回传拿不到 userCustomData。现双写两个 key（既有行为
不变，新增官方通道），使依赖 Taku 服务端激励回调做发奖关联的客户拿到自定义数据。

### 3. TB 线：transId 收敛为唯一来源（同设计原则）

`adapter/tb/TbRewardAdapter.m` 发奖回调的 transId 仅取 `WindMillRewardInfo.transId`
（ToBid "交易的唯一id"，与 ToBid 服务端激励回传同源），取不到为空串：

- 移除 alpha.3 的 UUID 兜底（伪造值，同上）；
- 移除 `thirdTransId` 混用（三方广告源标识，命名空间不同，无法与 ToBid 服务端回传
  配对）——仅在 `[TB_REWARD_DIAG]` 诊断日志中输出供排查；
- userCustomData 回传（load 入参快照）与 userId 兜底保持 alpha.3 行为不变。

### 4. 双线来源诊断日志

```text
[TK_REWARD_DIAG] reward: userId=<id> transId(len=<N>) src=<topon-show-id(reward-extra) | topon-show-id(show-captured) | none(平台未回传)>
[TB_REWARD_DIAG] reward: userId=<id> transId(len=<N>) thirdTransId=<三方标识或->
```

### 待真机回归（TK/TB 各一条激励视频）

1. TK：`src=` 应为 `topon-show-id(*)` 且 transId 非空；若出现 `none(平台未回传)`，
   持本文档与 Taku 支持确认展示回调 extra 的 `kATADDelegateExtraIDKey`。
2. TK：userId/userCustomData 客户端回传行为不变；如接了 Taku 服务端激励回调，验证
   回调 URL 中 user_custom_data 是否随 MediaExtraKey 通道回传（本版新增）。
3. TB：transId 非空（ToBid 交易id）且连续两次发奖互不相同；userCustomData 传入即回传。

## 升级指引（客户侧）

```ruby
# TK 客户
pod 'flame_sdk_ios', '1.0.1-alpha.4'
# ToBid 客户
pod 'flame_sdk_ios_tb', '1.0.1-alpha.4'
```

无需任何代码改动。注意：本版起 transId 不再本地伪造——平台未回传时为空串，接入方
服务端发奖逻辑需把"transId 为空"视为合法输入（不视为错误）。
